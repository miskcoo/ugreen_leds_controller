# DX4600 CLI support

The CLI recognizes the exact DMI product names `DX4600`, `DX4600+`, and
`DX4600 Pro`. On these models it scans SMBus/Synopsys adapters in numeric
order and accepts an MCU at address `0x3a` only after an SMBus WORD read of
register `0x5a` returns `0xc5b2`. It retries identification up to three times
with 100 ms delays, and uses four command attempts with 30 ms modification
retry delays. Other models retain the existing I801 selection and retry policy.

The timing and identification were recovered from the DX4600 stock
UGOS Pro 1.19.1.0126 LED module. The existing legacy I2C-block frame,
LED mapping, status checksum and strict ACK (`0x80 == 1`) are preserved.
The sysfs adapter name is read from `name`, falling back to `device/name`.
Failed candidates are closed before continuing the scan.

All CLI instances, including status reads, now share
`/run/ugreen-leds-cli.lock` for the full transaction. Contention fails after
approximately two seconds. This coordinates CLI processes only; the existing
requirement to unload the conflicting kernel LED module still applies.
Help does not require root or acquire the lock.

## Physical validation and limitations

On 2026-09-19 the LLLED_FPK user confirmed color switching, turning LEDs on,
and turning LEDs off on an exact **DX4600**, using application 2.1.2 and kernel
`6.18.18.c1032-trim`. The downstream CLI was built from upstream commit
`1e881da8b3d8598abadb50e859e8433c365c2840` with local patches, including the
DX4600 behavior ported here. Its version was
`ugreen_leds_cli 1e881da+llled-firmware-1.19` and SHA-256 was
`bfce4bfa9f4f819699e589292cd2287fae66cd0fcf4ef49268fcf7f9535f30c4`.

The recorded diagnostic selected SMBus I801 `/dev/i2c-1`, address `0x3a`,
legacy protocol, with successful power-status readback and ACK `0x01`.
The bus number is an observation, not a hardcoded requirement.

This report does not establish new physical validation for DX4600+ or
DX4600 Pro, and does not claim kernel-module validation. Intermittent ACK
`0x00`, historical timeouts/lock contention, and DesignWare arbitration
errors remain tracked downstream. An ioctl success or zero ACK must not
be treated as a successful LED command. On 2026-09-20, the contributor additionally confirmed that physical validation
had been completed. No additional build fingerprint or per-command test log
was supplied with that confirmation; the fingerprint above identifies the
earlier recorded downstream baseline.

## Regression tests

On an isolated Linux build machine, run `sh tests/test-cli.sh` (the lock tests
use sudo and refuse to replace an existing lock). The tests mock device
opens and SMBus ioctls to verify candidate order, exact model matching,
signature mismatch/read failures, retry counts, descriptor cleanup and
legacy I2C-block writes. CLI tests cover help and lock failure modes.
They do not write to NAS hardware and do not replace physical testing.
